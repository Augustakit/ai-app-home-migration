# Windows 应用数据目录跨盘迁移手册（Junction 法）

通用手册，与具体软件、机器、用户名、盘符、时间无关。文中所有路径均为占位符，替换后即可使用。配套说明见上一级目录 `README.md`。

---

## 0. 适用与不适用

**适用**：某个桌面应用把几个 GB 的运行时、插件、模型、素材、只读缓存写在系统盘的用户目录下，想搬到别的盘，又不希望重装或改配置。

**不适用**：

- 程序安装目录、`Program Files`、系统目录、Windows 目录
- 浏览器 profile 整体（书签、密码、Cookie、Local Storage、IndexedDB 都在里面）
- 云同步目录、加密/权限敏感目录
- 系统「已知文件夹」整体（桌面、文档、下载、视频等，带桌面配置与只读标记，常被资源管理器占用）
- 正在被写入的数据库、日志、会话、配置（**仅针对逐目录迁移**；整体 home 迁移在应用完全退出后会把它们随根目录一起搬走，不单独处理）

---

## 1. 一句话原理

用**目录联接（Junction）**把原路径变成一个指向新位置的透明入口。应用以为自己还在写原盘，实际数据落在别的盘。Junction 只对**本地 NTFS 目录**有效，创建它**不需要管理员权限**；符号链接才需要。

| 方式 | 对象 | 跨盘 | 需要管理员 | 应用感知 |
|---|---|---|---|---|
| Junction | 目录 | 可以 | 否 | 无 |
| 符号链接 | 目录/文件 | 可以 | 是 | 可能有 |
| 快捷方式 | 文件 | — | 否 | 有，不能用 |

**不要**用「复制粘贴 + 删原目录」代替：中途失败就是数据丢失，且没有退路。

## 2. 十条铁律

1. **先测量，别看文件夹属性**：以「文件数 + 总字节数」为判据。资源管理器对 Junction 显示的大小不可靠。
2. **目标根路径要短**：ASCII、无空格、无中文、本地固定盘、NTFS。深层 `node_modules` 很容易撞 260 字符路径上限。
3. **必须完全退出应用**：最常见失败原因。若迁移对象正是「当前托管你操作界面的那个应用」，**在该应用的会话内不可能完成**，必须由外部进程/脚本执行。
4. **优先整体，其次挑静态大块**：目标是「整个目录都不留在系统盘」时，用整体 home 迁移，一次连散文件、活跃目录和以后新建的内容都覆盖；只做逐目录迁移时，才限定于运行时、插件、模型、素材、只读缓存，把活跃数据库、日志、会话、配置留在原地。两种方案都要求应用完全退出。
5. **顺序不可变**：复制 → 双重校验 → 改名 → 建 Junction → 穿透验证。
6. **改名而不是删除**：旧目录改名保留为退路，全部验证通过前不许删。
7. **验证通过后，由用户选择备份怎么处理**：见第 5 节。脚本必须提供选项，不能替用户默认「自动删光」。
8. **空间用磁盘剩余空间核对**，不要用递归目录统计判断「有没有释放」——递归会穿透 Junction 把新盘的数据也算进去。
9. **全程可回滚**：任何时候都能删链接、把备份改回原名。
10. **失败即停**：任一项校验失败，立即回滚该项，不继续后续项；不要用「大概差不多」放行。

## 3. 该迁什么 / 不该迁什么

| 目录类型 | 能否迁 | 说明 |
|---|---|---|
| 运行时二进制（node、python、内置引擎） | 可以 | 静态、只读，体积大，收益高 |
| 插件市场与插件缓存 | 可以 | 静态；但应用运行中会写入/删除，必须退出后重建副本 |
| 模型、素材、只读资源包 | 可以 | 最安全 |
| 只读缓存（ShaderCache、Code Cache、网页 Cache） | 可以 | 会自动重建 |
| 威胁库 / 特征库 | 可以 | 静态 |
| 包管理器 store / cache | **优先用环境变量** | 改环境变量比 Junction 更干净 |
| 应用数据库、WAL、会话、配置 | **不要** | 正在写，迁移会造成新旧数据分裂 |
| 日志、traces、telemetry | **不要** | 持续写入 |
| Local Storage / IndexedDB / Cookies | **绝对不要** | 里面是界面设置与登录态，删了会丢配置 |
| 程序安装目录、`app-<版本>` 本体 | **不要** | 通过卸载/重装处理 |

---

> 补充：表里标「不要」的活跃目录（会话缓存、日志、traces、cache、projects）并非不能迁。它们同样可以建 Junction，且建好后写入会落到新盘、原盘不会重新占用；前提是**必须完全退出应用**，且要接受数据仍会持续增长、只是换个盘。根目录里的数据库、配置等散文件是文件不是目录，Junction 不适用，会留在原盘。配套入口见 `scripts/Migrate-ActiveDirs.bat`。

> **首选方案：整体 home 迁移。** 若目标是「整个应用数据目录都不在系统盘」，应把根目录本身改名留作退路、在原位置建一个指向目标盘的链接，而不是逐个目录建链接。逐目录方案有两个固有缺陷：小目录与散文件会被漏下；应用以后在根目录新建的任何内容仍会落回系统盘。整体迁移时先用 `robocopy 源 目标 /E /COPY:DAT /XJ` 复制剩余真实内容（`/XJ` 跳过已有链接，避免重复或循环），再改名根目录、建链接、逐项验证。**注意**：保留的退路目录里若含子链接，绝不能递归删除，否则会顺着链接删到目标盘数据。

### 3.1 整体 home 迁移：完整流程与实测结论

1. 完全退出应用，确认无残留进程；确认目标盘是本地固定盘且 NTFS。
2. 统计根目录顶层，区分**已有子链接**（早前逐目录迁移的成果）与**真实项目**（小目录、散文件）。
3. `robocopy <APP_HOME> <TARGET_ROOT> /E /COPY:DAT /XJ` 只复制真实项目，跳过已有子链接——它们的数据本来就在目标盘。
4. 逐文件校验：每个真实项目在目标侧都有同名副本，且「相对路径 + 长度」列表一致。
5. 根目录改名为 `<APP_HOME>.migbak` 留退路 → 原位置建一个指向 `<TARGET_ROOT>` 的 Junction。
6. 穿透验证：经原路径能读到全部数据；写入探针（临时文件）必须出现在目标侧，以此证明以后新建的内容不会再落回系统盘。
7. 重启应用自测；按第 5 节决定退路怎么处理。清退路前按 5.2 跑覆盖闸门，并确认退路里没有重解析点。

**实测结论**：整体迁移后，根目录顶层项目集合与目标盘完全一致，目标盘顶层没有嵌套链接；经原路径与直读目标路径的文件相对路径集合一致、静态文件双路径 SHA256 一致、创建时间戳一致；写入探针确认新文件直接出现在目标侧。系统盘只剩一个链接，占用近似为零。

**两次扫描对不上不等于出错**：应用运行时日志、数据库持续写入，先后两次递归统计的总字节数可能相差几 KB，活跃文件的哈希也可能不同。判据是「相对路径集合一致 + 静态文件哈希一致 + 写入探针通过 + 磁盘剩余空间符合预期」，而不是要求两次的总字节数完全相等。

配套脚本：`scripts/Migrate-WholeHome.ps1`（`-CleanupBackup` 默认关闭，开启后按「先删链接、再删内容」的安全顺序清退路）。首次运行保留退路时，之后想清除只需**再运行一次并加 `-CleanupBackup`**：脚本会识别根目录已是链接，自动进入清理模式，不需要退出应用，也不会重复迁移。

## 4. 标准流程（七步，逐目录方案）

占位符：`<APP_HOME>` 应用数据根目录、`<TARGET_ROOT>` 目标根、`<NAME>` 子目录名、`<PROCESS>` 应用进程名。

**第 0 步 · 准备**：完全退出应用（托盘退出 + 任务管理器确认无残留进程）；确认目标盘是本地固定盘且 NTFS；备份关键配置。

**第 1 步 · 测量现状**：统计每个目录的文件数与总字节数，记下来。

**第 2 步 · 安全复制（务必加 `/XJ`）**

```powershell
robocopy '<APP_HOME>\<NAME>' '<TARGET_ROOT>\<NAME>' /E /COPY:DAT /R:1 /W:1 /XJ /NFL /NDL /NJH /NJS /NP
if ($LASTEXITCODE -ge 8) { throw 'robocopy failed' }
```

`/XJ` 跳过已有 Junction，否则可能跟随链接造成循环或把新盘数据又复制一遍。`$LASTEXITCODE` 小于 8 才算成功（1 = 有文件被复制，是正常的）。

**第 3 步 · 双重校验**：文件数、总字节数都必须相等；更严格时，逐文件比较「相对路径 + 长度」列表（`Compare-Object` 结果必须为空）。**注意路径截取前先 `TrimEnd('\')`**，否则末尾带反斜杠会整体错位。

**第 4 步 · 改名留退路**

```powershell
Rename-Item -LiteralPath '<APP_HOME>\<NAME>' -NewName '<NAME>.migbak' -ErrorAction Stop
```

若报「访问被拒绝」：先查目录属性（已知文件夹常带 `ReadOnly`），清除后可重试；仍失败就是**句柄占用**，只能退出应用再做，不要硬删。

**第 5 步 · 建 Junction**

```powershell
$link = New-Item -ItemType Junction -Path '<APP_HOME>\<NAME>' -Target '<TARGET_ROOT>\<NAME>' -ErrorAction Stop
```

优先用 PowerShell 原生方式。`cmd /c mklink /J` 在很多受控环境里会被禁止，且需要拼接引号，容易出错。

**第 6 步 · 穿透验证**：`LinkType` 必须是 `Junction`，`Target` 指向正确，且**通过原路径**读到的文件数/字节与目标完全一致。

**第 7 步 · 跑完第 6 节验证清单，再由用户选择备份处理方式**（第 5 节）。

## 5. 备份、核对与清理（本手册的核心规则）

### 5.1 完整链路

```
备份（改名 .migbak）
  → 迁移 + 穿透验证
  → 核对备份内容（把 .migbak 与目标逐文件比对 + 抽样哈希）
  → 交给用户选择处理模式
  → 执行清理（可选：同时清冗余缓存副本）
  → 检查回收站 + 用磁盘剩余空间核对释放量
```

**顺序不能颠倒**：没有「核对备份内容」这一步就删备份，等于把唯一退路丢掉。

### 5.2 核对备份内容（硬闸门）

删除备份前，必须证明**目标目录已完整覆盖备份内容**：

1. `.migbak` 中每个相对路径在目标侧都存在；**允许目标侧多出文件**（应用重启后会继续往新盘写入）
2. `.migbak` 中最大文件在目标侧同路径存在，且 SHA256 一致
3. 该项 `LinkType = Junction`，目标是真实目录（本身不是链接）
4. 备份为空时直接拒绝删除

两个常见错误：

- 拿「通过 Junction 读到的源路径」和「目标路径」比对。这两个是**同一份数据**，无论目标有没有复制完整都会显示一致，是假闸门。必须拿**备份本体**去比。
- 要求备份与目标的文件数、字节数**完全相等**。迁移后应用会往新盘写新文件，这会让闸门永远失败、备份永远删不掉。正确关系是「备份 ⊆ 目标」。

### 5.3 交给用户的四种处理模式

脚本通过 `-CleanupMode` 提供选项，默认 **`Keep`（保留备份）**，绝不默认自动删除：

| 模式 | 行为 | 空间 | 可恢复 | 适用 |
|---|---|---|---|---|
| `Keep`（默认） | 保留 `.migbak` | 不释放 | 是 | 还想观察几天 |
| `Recycle` | 备份移入回收站 | **暂不释放** | 是 | 想留退路但不想看目录 |
| `Delete` | 永久删除备份 | 立即释放 | 否 | 验证全过、另有副本 |
| `Archive` | 移到指定归档目录 | 原盘释放 | 是 | 需要长期留证 |

另有 `-Interactive`：验证通过后列出摘要，让使用者现场按 `K / R / D / A` 选择。**交互式需要有人在场**，无人值守时用参数模式。

### 5.4 自动清理缓存与冗余副本

除了备份，迁移过程还可能留下：目标根下没被任何 Junction 引用的旧副本、重建副本时的残留、临时缓存目录。

用 `-PurgeOrphans` 可让脚本在核验后列出并清除这些冗余目录。安全约束：

- 默认关闭，必须显式开启
- 只处理目标根下**不在本次清单**里的普通目录
- 遇到 Junction 一律跳过（避免顺着链接删数据）
- 每个被删目录都先打印全路径，再执行

### 5.5 「删除」不等于「释放」

很多删除工具/安全钩子会把文件**移进回收站**而不是真正删除。表现是：备份目录不见了，但磁盘剩余空间纹丝不动。所以每次清理后必须：

1. 检查回收站的内容与体积
2. 确认里面没有其他需要保留的东西，再清空回收站
3. 用**磁盘剩余空间**核对释放量，而不是看目录大小

**不要**不加检查地清空整个回收站——那会连带删掉用户此前删除的其他文件。

### 5.6 清除顺序

验证清单全过 → 5.2 硬闸门 → 用户选定模式 → 执行 → 检查回收站 → 核对磁盘剩余空间 → 记录结果。

## 6. 验证清单（十项，别跳）

建议直接用 `scripts/Verify-Migration.ps1` 机械核验，它只读、输出 PASS/FAIL 汇总。上面十项针对**逐目录方案**。

**整体 home 模式下**，子目录不再是链接，上面第 1、4、5 项若照搬会全部误报失败。核验脚本会自动识别根目录是否为 Junction 并切换模式，检查项换成：根链接类型与 `ReparsePoint` 属性、`Target` 指向预期根、目标是真实目录且顶层无嵌套链接、顶层项目集合一致、逐文件路径集合一致、静态文件双路径哈希一致、写入探针（`-WriteProbe` 可选）、退路是否含子链接、磁盘剩余空间可读。

1. 每个原路径 `LinkType = Junction`，属性含 `ReparsePoint`
2. 每个目标是真实目录，无嵌套链接、无循环
3. `Target` 是预期的绝对路径
4. 逐文件「相对路径 + 长度」列表比对，`diff = 0`
5. 各目录最大文件经原路径与目标路径的 SHA256 一致
6. 核心二进制/数据库的版本元数据、大小可读
7. 应用其余目录（配置、数据库、日志）完好，时间戳在更新 → 应用读写正常
8. 没有多余副本目录；`.migbak` 状态与用户选定的处理模式一致
9. 应用重启后功能自测（插件、文档、运行时）通过
10. **磁盘剩余空间**增加量 ≈ 迁出数据量；回收站已按 5.5 处理

> 动态证据比静态证据更有力：迁移后让应用主动写几个新文件，再比对原路径与目标侧的结构是否仍一致。一致才说明新写入确实落在了新盘。

## 7. 回滚

```powershell
# 只删链接，不删数据。绝不要加 -Recurse
[System.IO.Directory]::Delete('<APP_HOME>\<NAME>', $false)

# 把备份改回原名
Rename-Item -LiteralPath '<APP_HOME>\<NAME>.migbak' -NewName '<NAME>'
```

如果备份已被删除，则从目标目录复制回原位置，再删除 Junction。最后可删除目标根目录。若备份被移到了回收站或归档目录，先从那里取回。

## 8. 常见坑（实测提炼）

1. **在应用内迁移应用自己的 home**：死结。退出后应用为了继续会话会立刻重启，进程始终存在。必须交给外部脚本。
2. **改名「访问被拒绝」**：先查 `Attributes` 是否带 `ReadOnly`（系统已知文件夹的常见标记）；清除后仍失败 = 句柄占用，只能退出应用。
3. **特殊文件夹别整体搬**：桌面/文档/下载/视频带 `desktop.ini`，常被 Shell 占用，且很多软件在里面放数据。
4. **应用边写边删**：副本永远追不上源，甚至会多出源里已删除的文件（`/E` 不删目标多余文件）。必须退出应用后**重建干净副本**，或用 `/MIR`（会删目标文件，慎用）。
5. **只看总数会漏**：文件数、字节数相同也可能结构不同，要做逐文件比对。
6. **删 Junction 加了 `-Recurse`**：会顺着链接删到目标数据。删链接一律用非递归删除。
7. **目标根路径太长**：深层 `node_modules` 撞 MAX_PATH，目标根尽量短。
8. **`cmd /c mklink` 被环境禁止**：改用 `New-Item -ItemType Junction`。
9. **脚本静默**：每个分支都要有输出，否则中途失败看不出卡在哪一步。
10. **空间没释放**：备份还在、或进了回收站、或用递归统计穿透了 Junction。
11. **误清 Local Storage**：界面设置与登录态会丢，且不能靠重装找回。
12. **没加 `/XJ`**：跟随已有 Junction 造成循环或重复复制。
13. **包管理器缓存**：用环境变量迁移比 Junction 干净，改完记得验证实际 store 路径。
14. **路径字符串比对失效**：某些工具按绝对路径识别会话/工作区，迁移后可能出现「未分组」，重开应用通常可解。
15. **假校验闸门**：见 5.2，同源对比等于没校验。
16. **路径末尾反斜杠**：截取相对路径前不 `TrimEnd('\')` 会整体错位。
17. **重建目标时没查链接**：若目标恰好是 Junction，递归删除会伤到链接指向的数据。
18. **二次运行只做清理时被整体跳过**：若已是 Junction 的项被记为「失败」或干脆不记录，「全部成功」的判断不成立，清理阶段会跳过。应记为「已存在」并纳入清理候选。
19. **演练时弹出交互询问**：`-WhatIf` 下若仍执行 `Read-Host`，无人值守的演练会挂起。交互前要判断演练状态与宿主是否可交互。
20. **尖括号占位符没替换就运行**：`<APP_HOME>` 里的 `<` `>` 在 Windows 路径中是非法字符，`Test-Path -LiteralPath` 会直接抛「路径中具有非法字符」，报得像脚本坏了；`<PROCESS>` 没替换时进程守卫会假通过（查一个不存在的进程名当然查不到）。运行前替换全部占位符，脚本应主动检查并给出人话提示。
21. **整体迁移后退路含子链接**：从已逐目录迁过的根目录改名而来时，退路里会带若干指向目标盘真实数据的链接。不要只查顶层 `LinkType`，要用 `Attributes -match 'ReparsePoint'` 递归确认；先非递归删链接、再删真实内容、最后非递归删退路根目录。任何时候都不要对含链接的目录用 `-Recurse`。
22. **只看 `LinkType` 判断链接**：某些环境下该字段不填充或返回空，`Attributes` 里的 `ReparsePoint` 才是可靠依据。删除前的判断要同时看两者，并递归检查子树。
23. **整体迁移后用逐目录核验脚本**：它要求「每个源路径都是 Junction」，而整体迁移后子目录是真实数据，十项会全部误报 FAIL。核验工具必须支持整体模式自动切换。
24. **活跃写入被当成数据不一致**：迁移完成后应用继续写日志和数据库，两次扫描的字节数、活跃文件哈希不同是正常现象，不要据此判定失败或反复重建副本。
25. **退路里残留应用已清理的旧文件**：审计 spool、一次性证书包、临时元数据等会在应用重启后从当前目录消失，但仍留在退路里。清理前区分「真遗漏」与「已清理」：当前路径已无该文件、功能正常、日志无相关报错，即可判定为旧内容而非迁移遗漏。
26. **安全钩子拦截递归删除**：部分环境会对 `Remove-Item -Recurse` 抛「fail closed」。改用 .NET 原生删除前，务必先确认目标树里没有重解析点；钩子拦截时通常已有部分条目被移进回收站，重跑前先复查当前状态，不要盲目从头再删一遍。
27. **二次运行清理时脚本直接退出**：若脚本在「源目录已是 Junction」处无条件退出，用户第二次运行加清理参数什么都不会发生，退路永远清不掉。清理逻辑要抽成可复用函数，并在源检查阶段就分流到清理模式；清理退路不需要应用退出。
28. **无 BOM 的 UTF-8 脚本含中文会乱码**：Windows PowerShell 5.1 默认按系统 ANSI 代码页读取 `.ps1`，无 BOM 的 UTF-8 中文会被解成乱码，某些字节还会破坏字符串引号，表现为莫名其妙的语法错误。含中文的脚本必须写成 UTF-8 with BOM，且带 `-WhatIf` 这类通用参数时要声明 `CmdletBinding(SupportsShouldProcess = $true)`。
29. **汇总行的运算符优先级**：`"...{0}..." -f (@($list).Count - $failed), $failed` 在 `List[object]` 上可能抛「参数类型不匹配」。把总数、通过数先算成显式整数变量，再传给 `-f`，并实测退出码。

## 9. 使用配套脚本

```powershell
# 0) 首选：整体 home 迁移（先演练，再去掉 -WhatIf）
.\scripts\Migrate-WholeHome.ps1 -SourceRoot '<APP_HOME>' -TargetRoot '<TARGET_ROOT>' `
    -GuardProcess '<PROCESS>' -WhatIf

# 0b) 正式执行；核验通过后加 -CleanupBackup 才会安全清退路
.\scripts\Migrate-WholeHome.ps1 -SourceRoot '<APP_HOME>' -TargetRoot '<TARGET_ROOT>' `
    -GuardProcess '<PROCESS>'

# 0c) 核验（自动识别整体模式；加 -WriteProbe 可验证新写入去向）
.\scripts\Verify-Migration.ps1 -SourceRoot '<APP_HOME>' -TargetRoot '<TARGET_ROOT>'

# 1) 逐目录方案：先演练，不改动任何东西
.\scripts\Migrate-AppDataDirs.ps1 -SourceRoot '<APP_HOME>' -TargetRoot '<TARGET_ROOT>' `
    -Directories @('binaries','plugins','cache') -GuardProcess '<PROCESS>' -WhatIf

# 2) 正式迁移（默认保留 .migbak 退路）
.\scripts\Migrate-AppDataDirs.ps1 -SourceRoot '<APP_HOME>' -TargetRoot '<TARGET_ROOT>' `
    -Directories @('binaries','plugins','cache') -GuardProcess '<PROCESS>'

# 3) 独立核验，只读，输出 PASS/FAIL
.\scripts\Verify-Migration.ps1 -SourceRoot '<APP_HOME>' -TargetRoot '<TARGET_ROOT>' `
    -Directories @('binaries','plugins','cache')

# 4) 核验通过后，由用户选择备份处理方式
.\scripts\Migrate-AppDataDirs.ps1 -SourceRoot '<APP_HOME>' -TargetRoot '<TARGET_ROOT>' `
    -Directories @('binaries','plugins','cache') -GuardProcess '<PROCESS>' `
    -CleanupMode Delete -PurgeOrphans

# 或者：让脚本列出摘要，现场按 K/R/D/A 选
.\scripts\Migrate-AppDataDirs.ps1 -SourceRoot '<APP_HOME>' -TargetRoot '<TARGET_ROOT>' `
    -Directories @('binaries','plugins','cache') -GuardProcess '<PROCESS>' -Interactive
```

参数说明：

| 参数 | 含义 |
|---|---|
| `-SourceRoot` | 应用数据根目录 |
| `-TargetRoot` | 目标根目录（短、ASCII、NTFS 本地盘） |
| `-Directories` | 要迁移的子目录名数组 |
| `-GuardProcess` | 应用进程名；检测到进程存在就拒绝执行 |
| `-BackupSuffix` | 备份后缀，默认 `.migbak` |
| `-CleanupMode` | `Keep` / `Recycle` / `Delete` / `Archive`，默认 `Keep` |
| `-Interactive` | 验证后现场询问，让用户选处理模式 |
| `-CleanupBackup` | 整体方案：覆盖闸门通过后按「先删链接、再删内容」安全清退路，默认关闭 |
| `-WriteProbe` | 核验脚本：写一个随即删除的探针文件验证新写入落盘位置，默认关闭 |
| `-ArchivePath` | `Archive` 模式的归档目录 |
| `-PurgeOrphans` | 额外清理目标根下的冗余副本目录，默认关闭 |
| `-RebuildTarget` | 目标已存在时允许先删除重建（用于修复脏副本） |
| `-WhatIf` | 演练，不改动任何东西 |

脚本会自动做：进程守卫 → 目标盘校验 → `/XJ` 复制 → 文件数/字节/结构三重校验 → 改名 → Junction → 穿透验证 → 失败单项自动回滚 → 备份内容硬闸门 → 按用户选择的模式清理 → 结构化结果表。

## 10. 术语

- **Junction / 目录联接 / ReparsePoint**：NTFS 上指向另一个目录的透明入口，仅限本地卷
- **穿透验证**：通过原路径（而非目标路径）读取数据，确认链接生效
- **`.migbak`**：改名保留的旧目录，回滚用的退路
- **`/XJ`**：robocopy 跳过 Junction，防止跟随链接
- **结构比对**：逐文件「相对路径 + 长度」列表的差分，比只比总数更严格
- **硬闸门**：删除备份前，用备份本体与目标做的完整性与哈希核对
